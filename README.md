# Afritop

Buy airtime, data bundles and prepaid electricity for Africa, paid in USDC from your own wallet. Right now that covers Nigeria, Ghana, Kenya and South Africa.

Payments settle on [Arc](https://docs.arc.io), Circle's stablecoin L1, and every transfer is verified on-chain before we deliver anything. Airtime goes out through [Africa's Talking](https://developers.africastalking.com). Data bundles and electricity tokens are generated by our own fulfillment pipeline, which is still simulated — see [what's real](#whats-real-whats-simulated).

Stack: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4, viem.

## Getting started

```bash
npm install
cp .env.local.example .env.local
npm run dev
```

> **This app moves real money.** There is no demo mode and no testnet: local
> development exercises the same Arc mainnet path as production. A full
> end-to-end test means a small real payment. The app refuses to create a
> payable order unless `USDC_RECEIVER` is set, so an unconfigured checkout is
> inert rather than dangerous.

## How a payment works

1. Build a top-up in the Buy flow.
2. Hit **Pay with USDC**. Your wallet pops up right away, no redirect. Have several wallets installed? A picker lets you choose (EIP-6963). No wallet at all? The page tells you where to get one.
3. The app asks your wallet to switch to Arc mainnet (it adds the network if it isn't there yet), then sends the exact USDC amount to the receiver.
4. We verify the transfer on-chain (`/api/confirm-usdc`), checking recipient, amount and sender against public RPCs.
5. Once verified, the top-up is delivered and you land on the receipt page.

### Two decimals, two log streams

Arc's USDC has a native interface (18 decimals, used for gas) and an ERC-20 interface (6 decimals, `0x3600…`), sharing one balance. Two consequences that the code depends on:

- Every USDC amount we move is parsed against the **ERC-20 interface at 6 decimals**. Never mix the two — raw values are off by 10¹².
- A single `transfer()` emits **two** `Transfer` logs with the same topic0: the ERC-20 contract's 6-decimal log, and an [EIP-7708](https://docs.arc.io/arc/references/usdc-system-events) 18-decimal log from the system emitter `0xffff…FfE`. `lib/usdc-verify.ts` therefore matches on the **emitter address**, not just the topic. Matching on the topic alone would read the amount 10¹² times too large.

Also worth knowing: Arc's mempool silently drops any transaction whose `maxFeePerGas` is below **20 Gwei**. A dropped transaction produces no error receipt and never appears in a block, which is why verification distinguishes "not indexed yet" from "never seen at all".

## Environment variables

Copy `.env.example` into Vercel → Project → Settings → Environment Variables. Everything marked required fails closed: without it the app refuses orders rather than taking money it can't deliver against.

| Variable | What it's for |
| --- | --- |
| `USDC_RECEIVER` | **Required.** Your EVM address for receiving USDC. Use a dedicated ops wallet. While unset, no order is payable. |
| `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` | **Required.** Durable order store. The serverless filesystem is ephemeral, and the one-transaction-per-order replay guard reads from this store — without it a consumed `txHash` can be forgotten and replayed. |
| `AUTH_SECRET` | **Required.** Any long random string (`openssl rand -hex 32`). Signs the wallet session cookie. |
| `AT_API_KEY` / `AT_USERNAME` | **Required for airtime.** Without both, airtime top-ups are refused — never credited as a simulation. `AT_USERNAME` is your app username; `sandbox` only works against the sandbox API. |
| `AT_ENV` | `live` for production airtime, `sandbox` for testing. |
| `CIRCLE_API_KEY` / `CIRCLE_ENV` / `CIRCLE_WEBHOOK_SECRET` | Deferred — not part of the mainnet launch. The wallet path is the single supported payment route. |
| `NEXT_PUBLIC_APP_URL` | Public base URL used for redirects. |

Support-chat extras (`RESEND_API_KEY`, `SUPPORT_EMAIL`, `SUPPORT_INBOUND_DOMAIN`, `SUPPORT_INBOUND_SECRET`) are documented in `.env.local.example`.

## What's real, what's simulated

- **Payments:** real on-chain USDC verification (`/api/confirm-usdc`) via public RPCs on Arc mainnet.
- **Airtime:** real through Africa's Talking. This is the only service we deliver today.
- **Data bundles & electricity tokens:** **simulated.** No vending partner is connected, so nothing is issued. Because customers pay real USDC, these services are labelled as simulated **before payment** — on the homepage, in the buy form, above the approve button, and on the receipt — and the order is flagged `simulated: true` in the store. That flag is what stops a receipt from implying a delivery that never happened.
- **Exchange rates:** live, from the free Frankfurter API, with a 2% spread on top of mid-market. `lib/fx-rates.ts` serves a 5-minute cache and then **fails closed** (503) rather than pricing real orders off a stale rate.

## Ordering and safety model

- **Fail closed on payments.** `paymentReceiver()` returns `null` unless `USDC_RECEIVER` is a valid, spendable address. `/api/checkout` and `/api/confirm-usdc` return 503 in that case, and the UI disables the pay button. The testnet build fell back to a burn address; that fallback is gone, because on mainnet it destroys funds.
- **Fulfillment only follows verified payment.** `/api/confirm-usdc` checks the on-chain transfer before anything is delivered. There is no client-callable path that fulfils an order without payment.
- **A delivery we can't perform is a failure, not a success.** If airtime delivery isn't configured, the order is marked `failed` so it surfaces for a refund instead of being silently credited.
- **One transaction pays for one order.** A replay guard rejects a `txHash` already used by another order.

## Project layout

```
app/
  page.tsx                    # landing page
  buy/                        # page.tsx (server: payment gate) + buy-flow.tsx (client)
  pay/[orderId]/              # connect wallet, pay USDC, confirm
  success/                    # receipt, electricity token, on-chain link
  transactions/               # order history, synced per wallet
  docs/                       # in-app documentation
  api/
    checkout/                 # validate and persist an order
    confirm-usdc/             # verify the transfer on-chain, then fulfil
    transactions/             # the signed-in wallet's history
    webhook/                  # Circle webhook, HMAC verified
    auth/                     # wallet sign-in and session endpoints
    stats/                    # delivery counts for the homepage chart
    fx-rates/                 # live USD to local-currency rates
lib/
  catalog.ts                  # countries, networks, distributors, bundles, delivery flags
  chains.ts                   # Arc mainnet config, USDC, receiver, payment guard
  usdc-verify.ts              # on-chain transfer verification (viem)
  africastalking.ts           # airtime client
  circle.ts                   # optional Circle hosted checkout (deferred)
  fulfill.ts                  # payment to delivery pipeline
  fx.ts / fx-rates.ts         # pricing maths and the live rate feed
  store.ts                    # order store: Redis, then JSON file, then memory
components/
  PayPanel.tsx                # wallet connect / switch / pay / confirm UI
tests/                        # focused tests for the money paths
```

## Notes

- Order history uses Upstash Redis. The JSON-file and in-memory fallbacks still exist for local development, but they are ephemeral on serverless hosts and must not be relied on in production — the replay guard depends on durable storage.
- Receipts are also saved in the browser, so they survive even when the server store comes up empty. Signing in with your wallet ties your history to an address instead of a device.
